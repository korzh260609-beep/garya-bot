# AI_MODEL_PRINCIPLE.md — Принцип СГ и ИИ-модели

Дата: 2026-05-02  
Статус: CANONICAL PRINCIPLE  
Владелец решения: Монарх Gary

---

## 0. Главный принцип

СГ — это название проекта Советника.

Сам по себе СГ не является самостоятельным интеллектом.

СГ становится умным только потому, что использует выбранную ИИ-модель.

На текущем этапе выбранная модель — GPT.

---

## 0A. Область применения принципа

Этот принцип применяется ко всем взаимосвязанным pillars, где описаны сущность СГ, поведение СГ, архитектура, Human Mode, Technical Mode, repo work, sources, AI routing, agents, modules и workflow.

Если где-то в pillars написано, что СГ думает, понимает, анализирует или является интеллектуальной системой, это нужно читать как сокращение:

```text
выбранная ИИ-модель обеспечивает reasoning/intelligence;
СГ как проектная система организует источники, память, правила, инструменты, порядок работы, права и ограничения вокруг модели.
```

Старые формулировки не должны пониматься так, будто СГ сам по себе является независимым интеллектом без выбранной модели.

---

## 1. Что даёт ИИ-модель

GPT уже является обученной умной моделью.

Её не нужно учить думать через большое количество кода, phrase-router, keyword-router, шаблоны ответов или ручное программирование мышления.

Модель уже умеет:

- понимать смысл;
- рассуждать;
- анализировать;
- объяснять;
- писать текст;
- работать с кодом;
- строить планы;
- делать выводы из данных;
- формулировать ответ на языке пользователя.

---

## 2. Что должен делать код СГ

Код СГ не должен заменять интеллект модели.

Код СГ должен организовывать правильную работу модели:

- давать модели реальные источники данных;
- давать модели актуальный контекст;
- давать модели память;
- давать модели правила проекта;
- давать модели порядок работы;
- давать модели инструменты;
- проверять права доступа;
- проверять риск действия;
- запрашивать подтверждение для state-changing действий;
- не позволять модели выдумывать факты без источника;
- не позволять опасные действия без разрешения монарха/пользователя.

В рамках Adaptive AI Routing 2.0 код СГ также может детерминированно выбирать **какой класс модели и какой уровень reasoning достаточны для конкретной задачи**. Это не считается программированием мышления: код не решает задачу вместо модели, а организует её выполнение, стоимость и границы.

Правило:

```text
если точный результат можно получить без LLM → использовать детерминированный путь;
если нужен AI → выбрать минимально достаточный tier и reasoning effort;
если результат валиден, но недостаточен → допускается ограниченная эскалация;
если provider технически недоступен → используется отдельный fallback-механизм.
```

---

## 3. Правильная формула

```text
СГ = проектная оболочка + правила + память + источники + инструменты + порядок работы + выбранная ИИ-модель
```

```text
Интеллект СГ на текущем этапе обеспечивается выбранной ИИ-моделью.
Код СГ не должен дублировать мышление модели.
Код СГ должен давать модели доступ, контекст, порядок и ограничения.
```

При наличии нескольких доступных моделей формула уточняется:

```text
СГ не обязан использовать одну и ту же модель для всех задач.
AI Router выбирает минимально достаточную модель/уровень reasoning,
не меняя семантическую архитектуру и не создавая второй интеллект в коде.
```

Конкретные названия моделей (например Luna/Terra/Sol или будущие аналоги) являются конфигурацией, а не бизнес-логикой SG.

## 4. Запрещённая ошибка

Запрещено строить СГ так, будто модель GPT глупая и её нужно учить разговаривать через готовые фразы.

Запрещено:

- создавать phrase-router как основной интеллект;
- создавать keyword-router как основной интеллект;
- создавать шаблонный ответчик вместо доступа к источникам;
- программировать разговор вместо организации работы;
- подменять работу с repo красивыми fallback-фразами;
- превращать source-state/debug output в нормальный пользовательский ответ;
- писать код, который пытается заменить reasoning-модель;
- создавать второй независимый AI Router рядом с каноническим;
- позволять модели самой повышать себе дорогой tier;
- прошивать конкретные provider model names в доменную бизнес-логику;
- считать длинный запрос автоматически сложным;
- считать слова `GitHub`, `memory`, `task`, `automation` достаточным основанием для выбора самой дорогой модели.

## 5. Правильный подход к repo

Для работы с repository СГ должен не заучивать ответы о repo, а получать реальные repo-факты.

Правильный порядок:

```text
запрос пользователя
-> выбранная ИИ-модель понимает смысл
-> СГ определяет, что нужны repo-факты
-> repo/source layer читает repository
-> модель получает verified facts
-> модель анализирует и отвечает
```

С Adaptive AI Routing этот порядок уточняется:

```text
если нужен только точный repo-факт (HEAD, branch, CI status, файл) → L0 без LLM;
если нужен обычный summary/review → L1/L2 по задаче;
если нужен сложный root-cause debugging или архитектура → L3;
```

Неправильный порядок:

```text
запрос пользователя
-> keyword/phrase match
-> готовый шаблонный ответ
-> отсутствие реального чтения repo
```

---

## 6. Практическое следствие

При разработке СГ приоритет должен быть таким:

1. доступ к источникам;
2. правильный порядок чтения данных;
3. verified facts;
4. проверка, нужен ли вообще LLM;
5. выбор минимально достаточного AI tier/effort;
6. передача фактов модели;
7. ограничения на действия;
8. только потом оформление ответа моделью.

Оформление ответа не должно становиться отдельным костылём вместо реальной работы.

Минимально достаточная модель означает **минимальную по стоимости/интенсивности модель, которая всё ещё надёжно выполняет задачу**. Экономия не имеет права снижать модель ниже требуемого уровня надёжности.
