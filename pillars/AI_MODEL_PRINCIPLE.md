# AI_MODEL_PRINCIPLE.md — Принцип СГ и ИИ-модели

Дата: 2026-05-02  
Статус: CANONICAL PRINCIPLE  
Владелец решения: Монарх Gary

---

## 0. Главный принцип

СГ — это название проекта Советника.

Сам по себе СГ не является самостоятельным интеллектом.

СГ становится умным только потому, что использует выбранную ИИ-модель.

На текущем этапе выбранная модель — GPT.

---

## 1. Что даёт ИИ-модель

GPT уже является обученной умной моделью.

Её не нужно учить думать через большое количество кода, phrase-router, keyword-router, шаблоны ответов или ручное программирование мышления.

Модель уже умеет:

- понимать смысл;
- рассуждать;
- анализировать;
- объяснять;
- писать текст;
- работать с кодом;
- строить планы;
- делать выводы из данных;
- формулировать ответ на языке пользователя.

---

## 2. Что должен делать код СГ

Код СГ не должен заменять интеллект модели.

Код СГ должен организовывать правильную работу модели:

- давать модели реальные источники данных;
- давать модели актуальный контекст;
- давать модели память;
- давать модели правила проекта;
- давать модели порядок работы;
- давать модели инструменты;
- проверять права доступа;
- проверять риск действия;
- запрашивать подтверждение для state-changing действий;
- не позволять модели выдумывать факты без источника;
- не позволять опасные действия без разрешения монарха/пользователя.

---

## 3. Правильная формула

```text
СГ = проектная оболочка + правила + память + источники + инструменты + порядок работы + выбранная ИИ-модель
```

```text
Интеллект СГ на текущем этапе обеспечивается выбранной ИИ-моделью.
Код СГ не должен дублировать мышление модели.
Код СГ должен давать модели доступ, контекст, порядок и ограничения.
```

---

## 4. Запрещённая ошибка

Запрещено строить СГ так, будто модель GPT глупая и её нужно учить разговаривать через готовые фразы.

Запрещено:

- создавать phrase-router как основной интеллект;
- создавать keyword-router как основной интеллект;
- создавать шаблонный ответчик вместо доступа к источникам;
- программировать разговор вместо организации работы;
- подменять работу с repo красивыми fallback-фразами;
- превращать source-state/debug output в нормальный пользовательский ответ;
- писать код, который пытается заменить reasoning-модель.

---

## 5. Правильный подход к repo

Для работы с repository СГ должен не заучивать ответы о repo, а получать реальные repo-факты.

Правильный порядок:

```text
запрос пользователя
-> выбранная ИИ-модель понимает смысл
-> СГ определяет, что нужны repo-факты
-> repo/source layer читает repository
-> модель получает verified facts
-> модель анализирует и отвечает
```

Неправильный порядок:

```text
запрос пользователя
-> keyword/phrase match
-> готовый шаблонный ответ
-> отсутствие реального чтения repo
```

---

## 6. Практическое следствие

При разработке СГ приоритет должен быть таким:

1. доступ к источникам;
2. правильный порядок чтения данных;
3. verified facts;
4. передача фактов модели;
5. ограничения на действия;
6. только потом оформление ответа моделью.

Оформление ответа не должно становиться отдельным костылём вместо реальной работы.

---

## 7. Связь с остальными pillars

Если другие pillars описывают СГ как самостоятельный интеллект без уточнения роли выбранной ИИ-модели, такие формулировки должны быть позже пересмотрены.

Правильное уточнение:

```text
СГ как проектная система организует работу.
ИИ-модель обеспечивает reasoning/intelligence.
Код СГ обеспечивает доступ, память, источники, порядок, безопасность и действия.
```

Изменение других pillars выполняется отдельно и только по решению монарха.
