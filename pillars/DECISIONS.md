# 0. ВЕРХОВНАЯ КОНЦЕПЦИЯ СГ

## D-000: СГ — свободная мультиюзерная сущность с управляемыми действиями

Статус: ПРИНЯТО  
Дата: 2026-04-30  
Область: ядро / философия / мультиюзерность / границы действий

СГ — это не просто бот, не набор команд, не помощник только для одного проекта и не система, зашитая под один репозиторий.

СГ — это гибкая мыслящая сущность, которая помогает пользователю думать, анализировать, создавать, разрабатывать, помнить контекст, вести проекты и предлагать решения.

СГ не должен быть жёстко привязан к:

- одному пользователю;
- одному репозиторию;
- одному workflow;
- одной папке;
- одному файлу;
- одному транспорту;
- одному набору команд;
- одному сценарию работы.

Главная формула:

```text
СГ свободен в мышлении.
СГ управляем в действиях.
```

СГ может свободно:

- думать;
- анализировать;
- предлагать;
- проектировать;
- сравнивать варианты;
- искать ошибки;
- искать риски;
- критиковать слабую логику;
- готовить планы;
- готовить тексты;
- готовить архитектуру;
- готовить код как предложение;
- готовить diff/patch как предложение.

СГ не может без явного разрешения пользователя:

- менять код;
- менять файлы;
- менять repo;
- менять pillars;
- менять БД;
- менять конфиги;
- делать commit;
- делать PR;
- делать deploy;
- писать комментарии/issue в GitHub;
- менять подтверждённую память как долговечный факт;
- удалять данные;
- отправлять сообщения от имени пользователя;
- выполнять внешние действия, которые меняют состояние.

Единственные жёсткие ограничения СГ:

1. СГ не принимает окончательное решение за пользователя.
2. СГ не вносит никаких изменений без явного разрешения пользователя.

Всё остальное должно управляться через режимы, capabilities, политики, настройки пользователя и контекст проекта, а не через вечные жёсткие запреты.

## D-000A: СГ — мультиюзерная система персональных сущностей

Статус: ПРИНЯТО  
Дата: 2026-04-30  
Область: мультиюзерность / изоляция / идентичность

СГ Core — общая основа системы.  
Личный СГ пользователя — персональная сущность для конкретного `global_user_id`.

Правильная модель:

```text
User A -> SG Instance A -> memory A -> projects A -> repos A -> settings A
User B -> SG Instance B -> memory B -> projects B -> repos B -> settings B
```

Каждый пользователь взаимодействует со своим СГ.

СГ одного пользователя не должен по умолчанию знать, раскрывать, использовать или подтягивать:

- память другого пользователя;
- проекты другого пользователя;
- репозитории другого пользователя;
- источники другого пользователя;
- настройки другого пользователя;
- историю взаимодействия другого пользователя;
- сам факт существования другого личного СГ как пользовательский контекст.

Контексты пользователей не должны пересекаться.

## D-000B: global_user_id — корень персональной логики

Статус: ПРИНЯТО  
Дата: 2026-04-30  
Область: identity / multi-transport

Вся персональная логика СГ должна идти от `global_user_id`.

Правильная схема:

```text
telegram_user_id \
discord_user_id  \
web_user_id       -> user_identities -> global_user_id -> users -> personal SG entity
github_user_id   /
email/login      /
```

`global_user_id` — настоящая личность пользователя внутри СГ.

Не являются корнем личности:

- `chat_id`;
- Telegram ID;
- Discord ID;
- GitHub ID;
- ID конкретного транспорта.

Они являются только каналами, ссылками или местами общения.

Если `global_user_id` есть — персональная память, project memory, настройки, роли, capabilities, источники и проекты ищутся через него.

Если `global_user_id` нет — СГ работает как guest и не подтягивает чужую память, project context Гарика или чужие данные.

## D-000C: Чаты и группы пользователя

Статус: ПРИНЯТО  
Дата: 2026-04-30  
Область: transport / chats / groups / memory

У одного пользователя может быть несколько личных чатов с СГ.

```text
global_user_id
  -> personal SG instance
    -> private_chat_1
    -> private_chat_2
    -> private_chat_3
```

Каждый чат — отдельное место разговора, но все они принадлежат одному пользователю через `global_user_id`.

У пользователя также могут быть группы с СГ в составе.

В группе:

```text
group_chat_id = место группового взаимодействия
global_user_id = личность конкретного участника
group_owner/admin = владелец/администратор группы
```

СГ в группе должен читать и видеть все сообщения, чтобы:

- понимать контекст разговора;
- понимать кто что сказал;
- видеть общую логику обсуждения;
- замечать риски;
- строить group context;
- помогать при необходимости;
- выполнять модерацию, если включён соответствующий режим.

Но чтение всех сообщений не означает ответ на каждое сообщение.

Активность СГ в группе управляется режимом группы.

Минимальные режимы:

1. `observer`  
   СГ читает всё, но отвечает только при упоминании, reply на СГ, команде или явном обращении.

2. `assistant`  
   СГ может активнее участвовать в группе, предлагать помощь и подключаться к обсуждению, но с лимитами/cooldown.

3. `moderator`  
   СГ следит за порядком, спамом, угрозами, токсичностью и правилами группы.

4. `sandbox`  
   Тестовый режим с большей свободой для разработки и экспериментов.

Личная память и групповая память разделены.

```text
personal memory != group memory
```

Групповая память хранит только общие факты/решения группы и не должна смешивать персональные контексты участников.

В группе СГ может понимать, что есть User A и User B, но не должен смешивать их личную память, проекты и настройки.

## D-000D: Граница контроля монарха

Статус: ПРИНЯТО  
Дата: 2026-04-30  
Область: governance / privacy / ownership

Монарх контролирует систему СГ, архитектуру, код, конфиги, роли, доступы, capabilities, модули, источники, биллинг и состояние системы.

Проект монарха и СГ монарха являются управляющим и разработческим контуром системы.

Но контроль системы не означает свободный доступ к приватной памяти пользователей по умолчанию.

Монарх может видеть и контролировать:

- архитектуру системы;
- код и репозитории проекта СГ;
- конфиги;
- роли;
- capabilities;
- доступы;
- системные логи и diagnostics;
- aggregate diagnostics;
- ошибки, abuse/security diagnostics;
- системное здоровье.

По умолчанию защищены от свободного просмотра:

- приватная личная память пользователя;
- приватные разговоры пользователя;
- приватная project memory пользователя;
- документы/источники пользователя;
- репозитории пользователя, если они подключены в его scope;
- личные настройки, не нужные для администрирования.

Исключительный доступ для безопасности, закона, abuse, отладки или поддержки должен быть явным, ограниченным, аудируемым и policy-controlled.

## D-000F: Workflow и источники — это смысл, а не путь

Статус: ПРИНЯТО  
Дата: 2026-04-30  
Область: sources / workflow / provider model

Workflow — это не файл и не папка.

Workflow — это источник смысла о процессе работы.

Он может быть представлен как:

- один файл;
- папка файлов;
- набор файлов;
- БД;
- GitHub source;
- Notion;
- Obsidian;
- API;
- внутренний UI;
- любой будущий provider.

Неправильно:

```text
workflow = folder
```

Правильно:

```text
workflow = source resolved by provider
```

СГ не должен жёстко знать, где лежит знание.

Правильная модель:

```text
смысловой запрос -> SourceResolver -> Provider/Adapter -> normalized result
```

## D-000G: Capabilities вместо вечных жёстких запретов

Статус: ПРИНЯТО  
Дата: 2026-04-30  
Область: permissions / capabilities / user control

СГ не должен быть сведен к постоянным allowlist/blacklist.

Правильная модель:

```text
capability = способность СГ
mode = текущий уровень свободы
permission = можно ли сейчас
confirmation = нужно ли явное разрешение
```

Примеры:

```text
think = всегда можно
analyze = всегда можно
suggest = всегда можно
prepare_code = можно как предложение
modify_repo = только после разрешения
deploy = только после разрешения
delete_data = только после разрешения
```

Пользователь может усиливать или ослаблять возможности своего СГ:

- включать capability;
- выключать capability;
- давать больше свободы;
- уменьшать свободу;
- разрешать авто-действия в пределах лимитов;
- требовать подтверждение для каждого действия.

Но финальные решения и внешние/state-changing действия требуют власти пользователя.

## D-000H: Команды — интерфейс, а не сущность СГ

Статус: ПРИНЯТО  
Дата: 2026-04-30  
Область: UX / commands / intent

Команды типа `/pm_set`, `/repo_status`, `/workflow_check`, `/price`, `/tasks` — это только интерфейсные ярлыки.

СГ не должен мыслить так:

```text
нет команды = нет способности
```

Правильный поток:

```text
пользователь говорит естественно
СГ понимает intent
СГ выбирает capability
СГ выбирает source/tool
СГ предупреждает о рисках
СГ спрашивает разрешение, если действие меняет состояние
СГ действует только после разрешения
```

## D-000I: СГ не должен быть trapped by regex

Статус: ПРИНЯТО  
Дата: 2026-04-30  
Область: meaning / intent / intelligence

Смысл СГ не должен зависеть только от keyword/regex проверок:

```text
если "repo" -> project
если "memory" -> memory
если "code" -> code
```

СГ должен понимать смысл фразы, а не только ключевые слова.

Regex/keyword могут быть вспомогательными быстрыми эвристиками, но не должны становиться клеткой для мышления СГ.

Статус: ПРИНЯТО  
Дата: 2026-04-30  
Область: future architecture / scope model

Целевая модель:

```text
global_user_id
  -> SG Instance
    -> User Profile
    -> User Memory
    -> User Settings
    -> Capabilities
    -> Chats
    -> Groups
    -> Workspaces
      -> Projects
        -> Project Memory
        -> Sources

        -> Project Settings
```

Минимальный scope project memory:

```text
global_user_id + project_id
```

```text
global_user_id + sg_instance_id + workspace_id + project_id
```

# 1. БАЗОВЫЕ РЕШЕНИЯ ЯДРА

## D-001: СГ предлагает и организует решения, пользователь/монарх принимает финальное решение

Статус: ПРИНЯТО  
Дата: 2026-01-11, уточнено 2026-04-30  
Область: core / governance

СГ может анализировать, предлагать, организовывать и формировать варианты решений.

Финальное решение всегда остаётся за пользователем или монархом в рамках его полномочий.

AI-операторы являются исполнителями/советниками, а не владельцами решений.

---

## D-002: Все AI-вызовы идут через централизованный router

Статус: ПРИНЯТО  
Дата: 2026-01-11  
Область: AI calls

Прямые вызовы моделей запрещены. Все AI-вызовы должны идти через единый router/обёртку с логированием, контролем модели, стоимости и причины вызова.

---

## D-003: Специализированные инструменты для сырой обработки, reasoning layer для смысла

Статус: ПРИНЯТО  
Дата: 2026-01-11, уточнено 2026-04-30  
Область: AI strategy

Специализированные инструменты используются для сырого извлечения/расчётов: OCR, STT, vision, market calculations, code tools и т.д.

Reasoning layer используется для смысла, планирования, синтеза, объяснения, проверки логики и принятия advisory-позиций.

Reasoning AI не должен заменять специализированные инструменты там, где есть точный инструмент, но не должен быть искусственно лишён роли мышления СГ.

---

## D-004: Каждый AI-вызов логируется с причиной и стоимостью

Статус: ПРИНЯТО  
Дата: 2026-01-11  
Область: observability / billing

Каждый AI-вызов должен логировать модель, примерную/фактическую стоимость, токены и причину использования.

---

## D-005: BehaviorCore независим от AnswerMode

Статус: ПРИНЯТО  
Дата: 2026-01-11  
Область: behavior

BehaviorCore определяет личность, риск-логику и базовое поведение. AnswerMode управляет только длиной ответа.

---

## D-006: Режимы ответа не меняют личность СГ

Статус: ПРИНЯТО  
Дата: 2026-01-11  
Область: UX

Short/normal/long отличаются длиной, а не личностью, логикой или принципами СГ.

---

## D-007: Неясный intent — максимум одно уточнение, если без него опасно действовать

Статус: ПРИНЯТО  
Дата: 2026-01-11, уточнено 2026-04-30  
Область: interaction

Если intent неясен, СГ может задать максимум один мягкий уточняющий вопрос.

Если можно безопасно дать варианты или объяснить предположение без действия — СГ может не спрашивать, а дать осторожный ответ.

Если действие может изменить состояние или привести к ошибке — нужно уточнение/подтверждение.

СГ говорит понятно и без унижения пользователя, но риски, ошибки логики и ограничения показывает прямо.

Статус: ПРИНЯТО

Область: architecture governance

Архитектурные изменения сначала обсуждаются и согласуются с монархом.

## D-011: Stage gates управляют внедрением, но не мышлением СГ

Статус: ПРИНЯТО  
Дата: 2026-01-11, уточнено 2026-04-30  
Область: roadmap

Stage gates запрещают внедрять будущие функции раньше этапа без решения монарха.

Но СГ может думать о будущей архитектуре, предлагать варианты и предупреждать о рисках.

Stage gate ограничивает реализацию, а не мышление.

## D-012: Transport layer тонкий и stateless

Статус: ПРИНЯТО  
Дата: 2026-01-11  
Область: transport / multi-channel

Transport layer не содержит бизнес-логики, памяти и прав. Он только адаптер между каналом и Core.

## D-013: Global identity важнее platform identity

Статус: ПРИНЯТО  
Дата: 2026-01-11, усилено D-000B  
Область: identity

Роли, permissions, память, проекты, настройки и capabilities должны идти от `global_user_id`.

Platform IDs — только связи с транспортами.

---

## D-014: Chat History — не Memory

Статус: ПРИНЯТО  
Дата: 2026-01-11  
Область: memory

Chat History — это история/лог для восстановления и recall. Memory — это curated semantic long-term knowledge.

Сырой чат нельзя бесконтрольно вставлять в prompt как память.

---

## D-015: Privacy-first recall и user isolation

Статус: ПРИНЯТО  
Дата: 2026-01-11, усилено 2026-04-30  
Область: privacy / recall

Cross-group/cross-context recall должен защищать identity.

User isolation важнее удобства recall.

Личная память одного пользователя не должна попадать в prompt другого пользователя.

---

## D-016: Корректность системы ограничивает действия, а не мышление

Статус: ПРИНЯТО  
Дата: 2026-01-11, уточнено 2026-04-30  
Область: global

System correctness, safety и predictability важнее опасной автономности.

Но это не должно запрещать СГ думать, анализировать, предлагать и проектировать. Ограничение относится к действиям и внедрению.

# 9. ТЕКУЩИЕ ИЗВЕСТНЫЕ ТОЧКИ ДАВЛЕНИЯ В КОДЕ

Эти места не обязательно являются немедленными багами, но их нужно постепенно привести к новой концепции:

1. `MeaningEngine` слишком зависит от keyword/regex-like domain detection.
2. `ProjectContextEngine` использует regex-like signals для глубины анализа.
3. `ToolSelectionEngine` выбирает инструменты через fixed intents.
4. `permissions.js` использует code allowlists вместо полной dynamic capability policy.
5. `cmdActionMap.js` привязывает abilities к командам.
6. `ActiveProjectContextResolver` содержит default `garya-bot` assumptions.
7. `ProjectRestoreService` всё ещё содержит workflow-folder/source-path логику.
8. `ProjectEvidenceTriggerPolicy` использует trigger/depth allowlists, которые должны развиться в dynamic policy/cost/permission decisions.
