# DECISIONS.md — Единые решения SG 2.0

> AGENT NOTE:
> This file is the canonical decisions file for SG 2.0.
> Read it before changing architecture, pillars, workflow, permissions, repo behavior, AI behavior, memory, sources, or external actions.
> Do not weaken, bypass, rename, delete, or contradict these decisions without explicit Monarch approval.

Дата создания: 2026-05-03  
Статус: CANONICAL  
Владелец: Монарх Gary / GARY

Этот файл фиксирует верхнюю философскую и архитектурную основу SG 2.0.

SG 2.0 создаётся как чистая новая ветка, а не копия старого проекта.

Главная формула:

```text
ИИ-модель свободна в мышлении.
СГ управляем в действиях.
Код СГ не заменяет интеллект модели, а организует её работу.
```

---

## D-000: СГ — проектная система Советника

Статус: ПРИНЯТО  
Область: философия / сущность / архитектура

СГ — не просто Telegram-бот, не один файл, не один агент, не workflow и не repository.

СГ — это проектная система Советника GARYA:

- правила;
- память;
- источники;
- инструменты;
- интерфейсы;
- модули;
- политики;
- порядок работы;
- выбранные ИИ-модели.

Telegram, GitHub, Render, база данных, агенты, источники и будущие интерфейсы — это части СГ, но не весь СГ.

---

## D-001: ИИ-модель является reasoning/intelligence layer

Статус: ПРИНЯТО  
Область: AI / reasoning / implementation

На текущем этапе интеллект и рассуждение даёт выбранная ИИ-модель.

Код СГ не должен пытаться заменить reasoning-модель большим количеством phrase-router, keyword-router, regex-ответов или шаблонных фраз.

Правильная модель:

```text
СГ = проектная оболочка + правила + память + источники + инструменты + порядок работы + ИИ-модель
```

ИИ-модель обеспечивает:

- анализ;
- рассуждение;
- объяснение;
- синтез;
- поиск рисков;
- подготовку планов;
- подготовку кода, diff или patch как предложения.

Код СГ обеспечивает:

- доступ;
- память;
- источники;
- порядок работы;
- безопасность;
- права;
- подтверждения;
- выполнение разрешённых действий.

Запрещено:

- строить код так, будто модель нужно учить думать готовыми фразами;
- делать keyword-router главным интеллектом;
- делать phrase-router главным интеллектом;
- программировать живое общение вместо организации работы;
- подменять реальные источники красивыми fallback-ответами.

## D-002: Living SG only

Статус: ПРИНЯТО  
Область: identity / UX / external behavior

У SG 2.0 есть одна внешняя сущность:

```text
Living SG / Советник GARYA
```

Запрещено создавать для пользователя отдельный внешний технический режим, raw console personality или вторую личность СГ.

Разрешено внутри системы:

- диагностика;
- логи;
- repo-анализ;
- тесты;
- debug-инструменты;
- архитектурные проверки.

Правило:

```text
Техническая способность внутри.
Живой СГ снаружи.
```

---

## D-003: Meaning-first

Статус: ПРИНЯТО  
Область: intent / routing / behavior

СГ не должен работать по схеме:

```text
keyword -> reflex response
```

Правильная схема:

```text
user message -> meaning -> intent -> context -> permission -> source/tool -> answer/action
```

Команды и короткие сигналы могут быть удобными ярлыками, но не должны быть основой мышления СГ.

Пользователь говорит естественно.  
СГ понимает смысл.

---

## D-004: State-changing действия только после разрешения

Статус: ПРИНЯТО  
Область: safety / repo / external state

СГ может свободно:

- читать;
- анализировать;
- объяснять;
- искать риски;
- предлагать;
- готовить планы;
- готовить код, diff или patch как предложение.

СГ не может без явного разрешения монарха:

- менять файлы;
- менять repository;
- менять pillars;
- менять workflow;
- менять конфиги;
- менять базу данных;
- делать commit;
- делать PR;
- делать deploy;
- удалять данные;
- менять Render/runtime contract;
- отправлять внешние сообщения от имени пользователя;
- выполнять любые другие state-changing действия.

Для GitHub-записи действует отдельное правило:

```text
Запись в repository выполняется только после финального разрешения монарха.
```

## D-006: Privacy и изоляция пользователей

Статус: ПРИНЯТО  
Область: privacy / multiuser / memory

SG 2.0 проектируется как мультиюзерная система.

Память, проекты, repositories, источники, настройки и личный контекст пользователей не должны смешиваться.

Правильная модель:

```text
User A -> Personal SG A -> memory A -> projects A -> sources A -> settings A
User B -> Personal SG B -> memory B -> projects B -> sources B -> settings B
```

Монарх владеет системой, но приватность пользователей должна быть защищена политиками доступа, логированием и явными процедурами.

## D-007: global_user_id — будущий корень личности

Статус: ПРИНЯТО  
Область: identity / multi-transport

SG 2.0 должен быть готов к нескольким transport layers.

Telegram ID, GitHub ID, Discord ID, chat_id и другие platform-specific IDs не должны становиться вечным корнем личности.

Целевая модель:

```text
platform_user_id -> user_identities -> global_user_id -> Personal SG
```

На раннем этапе допускается временное использование Telegram ID, но архитектура не должна быть заперта на Telegram.

## D-008: Проект Гарика не является default для всех

Статус: ПРИНЯТО  
Область: multi-project / user isolation

`garya-bot` — это проект монарха и внутренний проект разработки SG.

Он может быть default-контекстом только для Гарика при работе над SG.

Обычные пользователи не должны автоматически получать:

- repository Гарика;
- workflow Гарика;
- project memory Гарика;
- development context Гарика.

Если у пользователя нет активного проекта, SG работает как универсальный помощник.

## D-009: Workflow — источник смысла, а не только файл

Статус: ПРИНЯТО  
Область: workflow / sources / provider model

Workflow — это источник смысла о порядке работы.

На старте SG 2.0 workflow хранится в:

```text
pillars/workflow/
```

В будущем workflow может быть получен через Source Layer из файла, папки, базы данных, GitHub, Notion, Obsidian, внутреннего UI, API или другого provider.

Правильная модель на будущее:

```text
meaning request -> SourceResolver -> Provider/Adapter -> normalized result
```

## D-010: Capabilities, permissions и confirmations

Статус: ПРИНЯТО  
Область: permissions / actions / control

СГ должен управляться через:

- capability — способность;
- permission — можно ли сейчас;
- confirmation — нужно ли подтверждение;
- policy — правило выполнения.

Примеры:

- `think` — можно;
- `analyze` — можно;
- `suggest` — можно;
- `prepare_code` — можно как предложение;
- `modify_repo` — только после разрешения;
- `deploy` — только после разрешения;
- `delete_data` — только после разрешения.

## D-011: Source-first

Статус: ПРИНЯТО  
Область: factuality / sources / analysis

ИИ не является источником истины.

SG должен опираться на реальные источники, когда задача требует фактов:

- repository/runtime;
- API;
- RSS;
- web;
- документы;
- базы данных;
- пользовательские источники;
- сохранённая память.

ИИ используется для анализа, объяснения, синтеза, проверки логики и формулирования результата.

---

## D-012: Память имеет слои

Статус: ПРИНЯТО  
Область: memory / project context / recall

Chat History, Memory, Project Memory и Pillars — разные слои.

- Chat History — история сообщений.
- Memory — подтверждённая долговременная семантическая память.
- Project Memory — рабочий контекст конкретного проекта.
- Pillars — каноническая правда проекта.

Запрещено:

- сырой чат считать подтверждённой памятью;
- Project Memory использовать вместо Pillars;
- raw repo code хранить как обычную память;
- смешивать память разных пользователей.

---

## D-013: AI-вызовы идут через единый wrapper/router

Статус: ПРИНЯТО  
Область: AI calls / cost / observability

Прямые вызовы моделей в разных местах проекта запрещены.

Каждый AI-вызов должен в будущем проходить через единый AI wrapper/router и иметь:

- модель;
- причину;
- cost level;
- user/project scope;
- логирование;
- учёт токенов и стоимости, когда модуль billing будет готов.

AI operator/model не является SG.
AI operator/model — reasoning/intelligence layer и инструмент SG.

## D-015: Stage gates ограничивают внедрение, но не мышление

Статус: ПРИНЯТО

Потом конфиг.

## D-016: Чистая модульность

Статус: ПРИНЯТО  
Область: repository / core / modules

SG 2.0 не должен строиться как монолит.

Core координирует модули, но не поглощает их логику.

Запрещено:

- складывать всё в `index.js`;
- смешивать transport, AI, memory, sources, tasks, permissions и config;
- добавлять feature-логику прямо в core;
- менять core ради каждого нового модуля.

Разрешено:

- добавлять отдельные модули;
- подключать их через registry/config;
- расширять интерфейсы осторожно;
- менять core только после анализа и решения монарха.

---

## D-017: Pillars должны быть короткими, живыми и управляемыми

Статус: ПРИНЯТО  
Область: docs governance / pillars

Pillars — это не архив и не свалка идей.

Pillars должны фиксировать только то, от чего зависит будущая работа:

- решения;
- правила;
- границы;
- контракты;
- риски;
- порядок работы;
- source-of-truth;
- governance.

Если новый документ создаёт зависимости на несуществующие файлы, он должен быть отложен или адаптирован.

---

## D-018: Старый main — источник деталей, не шаблон для копирования

Статус: ПРИНЯТО  
Область: migration / repo cleanup

Старый `main` содержит полезные решения, код и документы.

Но SG 2.0 не должен копировать старый проект целиком.

Правильная миграция:

```text
main -> анализ -> решение -> адаптация -> перенос в dev/v2-start
```

Запрещено:

- переносить старую кашу в новую ветку;
- копировать файлы без обсуждения;
- восстанавливать старую структуру без причины;
- ломать чистый старт SG 2.0.
