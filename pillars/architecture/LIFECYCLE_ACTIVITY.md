# SG 2.1 — Lifecycle Activity (LA) Architecture

Status: ACCEPTED ARCHITECTURE / PLANNED / NOT IMPLEMENTED

## Purpose

Lifecycle Activity (LA) is the transport-independent append-only activity-history layer for significant SG actions. It answers: what SG actually did, when, where, for whom, against which entity, and with what result.

LA is not Memory 2.0, Project Memory/PDK4, Automation, Observability telemetry, diagnostics, or an execution orchestrator. It records concise activity facts and links back to authoritative domain entities rather than copying their state.

## Core invariant

Existing subsystems never depend on LA for successful execution.

```text
Domain/Capability Runtime
        |
        +-- performs authoritative work
        |
        +-- safeRecordActivity(event)
                    |
                    v
              Activity Store
```

Failure to record LA data must not roll back or block the authoritative action. Recording failure is itself observable through the existing observability/error path.

## Canonical event contract

```text
ActivityEvent
- id
- globalUserId?          canonical actor/user scope when applicable
- eventType              domain.entity.action
- category
- action
- status
- importance
- visibility
- title
- summary?
- source
- sourceId?
- workspaceId?
- transport?
- entityType?
- entityId?
- parentEventId?
- correlationId?
- startedAt?
- completedAt?
- createdAt
- metadata               bounded JSON
```

Minimum required fields: `id`, `eventType`, `category`, `action`, `status`, `title`, `source`, `createdAt`.

## Event naming

`eventType` uses a stable hierarchical namespace:

```text
domain.entity.action
```

Examples:
- `github.commit.created`
- `github.push.completed`
- `github.ci.completed`
- `task.started`
- `task.completed`
- `automation.updated`
- `memory.fact.updated`
- `ai.request.completed`
- `telegram.message.sent`
- `system.deploy.completed`

Consumers may filter by exact type or namespace prefix such as `github.*` without schema changes.

## Common enums

Status:
- `started`
- `success`
- `failed`
- `cancelled`
- `skipped`
- `partial`

Importance:
- `low`
- `normal`
- `high`
- `critical`

Visibility baseline:
- `private`
- `workspace`
- `system`

Categories are extensible stable labels such as `development`, `automation`, `memory`, `communication`, `ai`, `system`, `security`, `data`, `integration`.

## Correlation and hierarchy

`correlationId` groups all activity generated by one logical instruction/run/operation. `parentEventId` optionally expresses parent-child structure.

Example:

```text
task.started
  |- github.code.changed
  |- github.commit.created
  |- github.push.completed
  |- github.ci.completed
  `- task.completed
```

This permits future activity timelines and graphs without changing domain stores.

## Entity linking

`entityType` + `entityId` link LA to authoritative entities such as task, commit, automation, memory record, conversation, deployment or workspace. LA must not become a duplicate domain database.

## Multi-user / multi-workspace / multi-transport

The contract reserves `globalUserId`, `workspaceId` and `transport` from the first version. They may be null where not applicable, but their semantics remain canonical so future Telegram/Web/API/Discord/native-interface activity uses the same store and query model.

Identity, scope, access, Resource Authority and Action Gate remain authoritative. LA visibility never grants access to the underlying entity.

## Metadata discipline

`metadata` is bounded, redacted JSON for event-specific attributes that do not justify new stable columns. Secrets, raw credentials, unnecessary private content, large payloads and copied authoritative objects are forbidden.

## Meaningful-event rule

LA records meaningful actions/state transitions only. It must not log every function call, SQL query, cache operation or internal helper invocation.

Typical eligible events:
- user-visible task/action lifecycle changes;
- external integrations and mutations;
- meaningful state changes;
- significant AI execution summary/provenance references;
- important system transitions;
- failures of meaningful actions.

## Persistence and query boundary

Initial implementation uses the existing PostgreSQL persistence boundary with an append-oriented `activity_events` table and indexed query fields. No second database, queue, worker or microservice is introduced.

Canonical APIs:

```text
recordActivity(event)
safeRecordActivity(event)
getRecentActivity(filters)
```

Query filters are designed from the start for time range, event type, category, source, status, importance, workspace, transport, entity and correlation ID.

## Relationship to existing systems

- Memory 2.0: memory stores durable knowledge/context; LA stores activity events.
- PDK4: PDK4 stores evidence-backed project-development knowledge; LA may provide activity evidence references but cannot promote itself to project truth.
- Observability: telemetry/debug/audit traces explain runtime behavior; LA is the human-meaningful activity history. LA recording failures use existing observability.
- Automation: automation remains authoritative for workflow definitions/runs; LA links to automation IDs and summarizes meaningful lifecycle events.
- GitHub: GitHub development remains authoritative in GitHub state; LA records concise linked activity.
- AI Router: AI Router remains authoritative for model/cost provenance; LA may reference a completed AI activity but does not duplicate cost accounting.

## Retention extensibility

The schema and query boundary must permit future retention/archival policy by importance/category without implementing automated deletion in LA1. Historical retention must never silently delete authoritative domain state because LA is not that state.

## Future-compatible extensions

The LA core must support additive future stages without redesign:
- cross-system timelines;
- activity analytics;
- semantic activity search;
- event subscriptions;
- privileged audit views;
- activity graph visualization;
- native SG interface views;
- archival/retention tiers.

These extensions are not part of LA1-LA3 unless separately accepted.

## Non-goals for LA1-LA3

Do not introduce Kafka/Redis Streams, a new event bus, embeddings, a graph database, a new scheduler/worker, a standalone microservice, automatic daily reports, or broad runtime instrumentation.
